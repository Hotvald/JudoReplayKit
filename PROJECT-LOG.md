# JudoReplayKit — Project Log

Last updated: 2026-11-15

## Purpose

JudoReplayKit is a portable Windows application intended to help judo referees review match sequences without interrupting the match, live stream, or continuous recording.

The application UI and user-facing documentation are to be written in English. Development discussions may be in Danish.

## Core decisions

- **Replay model:** replay is an overlay on top of the live picture. Replay must be independent of the live stream and recording.
- **Immediate access:** replay should be available with minimal delay, especially for quick confirmation of a referee decision.
- **Continuous recording:** video must be recorded continuously to a user-selected storage location so a sequence can be retrieved later, even if no bookmark was created at the time.
- **Bookmarks:** bookmarks mark moments for later retrieval. Creating a bookmark must not automatically open the bookmark drawer.
- **Production safety:** the known-working production installation must not be changed during testing or repair work. Development changes are isolated in the Rev.8 test installation.

## 2026-11-08 — Independent review comparison: Gemini and DeepSeek Rev.9 proposals

**Source:** Complete reviewer texts supplied by the owner in the project conversation. **Reviewer attribution:** Gemini and DeepSeek. **Additional assessment:** ChatGPT. **Status:** Review findings only; no specification approval and no implementation authorization.

### Overall assessment

- DeepSeek supplied the more complete and test-oriented of the two reviewer proposals. Its strengths are explicit requirement IDs, a more detailed bookmark/persistence contract, clearer failure states, a broad acceptance-test matrix, and explicit acknowledgement of technical limitations.

### DeepSeek proposal — strengths and issues to resolve

**Useful contributions to incorporate or evaluate:**
- Make the selected replay interval contract explicit and test UI selection, requested interval, returned media interval and actually presented interval separately.
- Define bookmark persistence as a server-owned service/API with stable identifiers, validation, atomicity/transactions, concurrency and recovery.
- Give replay, archive and bookmark failures distinct machine-readable states rather than a generic failure.
- Explicitly test archive discovery when a camera is offline, interrupted recording, post-roll pending/partial states, long-running sessions and two-client bookmark writes.
- State honestly that browser frame stepping may be approximate unless the chosen media pipeline proves exact decoded-frame stepping.
- Measure two-camera offset and drift rather than assuming a common PC UTC clock guarantees capture synchronization.
- Keep camera ingest network exposure separate from UI, management and metrics exposure.

**Corrections/caveats:**
1. The proposed duration formula and requirement for exactly one request with duration=15.000 are too prescriptive before the actual archive API/media semantics are selected. A media container's reported duration may differ from the requested/presented interval. Specify the user-visible interval and a measurable presentation tolerance first; then choose whether exact-range retrieval or larger-span retrieval plus trimming is the implementation contract.
2. The requirement that video.duration equal the requested duration within ±0.1 s is not by itself a valid proof of correct interval or visible decode. It must be paired with timestamp/decoded-frame evidence and visible presentation.
3. The 30 s pre-roll + 15 s post-roll bookmark rule is not approved. Earlier discussions considered 30 s before and approximately 10–15 s after, but the final behavior remains an owner decision.
4. clickTimeMs, server time, recording-span end and capture time are not interchangeable. The bookmark schema must define the time source and mapping to each camera's archive timeline; a server timestamp alone does not establish the exact captured frame time.
5. Storing a single bookmarks.json in the recording folder and using temp/fsync/rename is one possible design, not a settled architecture. Filesystem semantics, concurrent writers, backups, removable drives and database recovery must be evaluated before selecting it.
6. The proposed ±5 s tolerance, 500 ms seek response, 8 s seek timeout, 15 s decode timeout, exact 1/30-second step semantics and other numeric thresholds need a reference platform and measurement method. Do not turn them into binding targets without owner approval.
7. The frame-step acceptance test allowing either 20 visibly different frames or an APPROXIMATE label is not sufficient. The test must verify the declared stepping behavior and label honestly; an approximate label cannot substitute for a working control.
8. The synchronization proposal should not assume that a manual visible marker automatically records each phone's actual capture-frame timestamp. The mechanism must be technically defined and validated; otherwise describe it as a calibration aid, not guaranteed synchronization.
9. The proposed support matrix, Basic authentication, localhost defaults, portable ZIP and sidecar choice are proposals only.

### Gemini proposal — strengths and issues to resolve

**Useful contributions to incorporate or evaluate:**
- Separate responsibilities for ingest, live delivery, recording/archive, replay, bookmark persistence, UI and lifecycle management.
- Require recording-health evidence based on actual write progress, not merely an open port or configured path.
- Require replay failures to be contained so they cannot interrupt recording or ingest.
- Evaluate a simple launcher before deciding that a compiled Supervisor is needed.
- Keep disk-full behavior technically honest and do not promise that an in-progress file can never be partial.

**Corrections/caveats:**
1. Gemini's statement that the core conflict is specifically HLS/WebRTC plus fMP4 writes is not established as a product requirement. Rev.9 must compare media/transport options rather than inherit Rev.8 technologies.
2. fMP4 does not, by itself, guarantee recovery up to the second after sudden power loss. Segment finalization, fragment/index structure, write buffering and recovery behavior must be specified and tested.
3. The proposed 1-second replay opening target and 3-second live-delay target are not approved. “Replay available” must be defined as first visibly presented frame, and tested on named reference hardware/network/browser conditions.
4. The proposal to bind both RTMP ingest and the UI proxy to 0.0.0.0 is unsafe as a blanket rule and conflicts with the need to restrict management exposure. Each endpoint/interface must have an explicit exposure policy. The example RTMP port 1936 is not established; Rev.8 used 1935, but neither port is mandated for Rev.9.
5. Automatic deletion of the oldest recording below 10 GB and default 30-day retention are destructive proposals and are explicitly unapproved. They must not be adopted without an owner-approved deletion policy, protected/locked tournament rules and recovery safeguards.
6. A compiled Supervisor, Node/Python sidecar, Caddy and MediaMTX are candidate components, not approved architecture. Their need and responsibilities must be justified against simpler alternatives.
7. The proposed storage-recovery acceptance test that fills a disk to 99% and expects automatic deletion is unsafe until deletion policy is explicitly approved.

## 2026-11-15 — MediaMTX live-edge playback and WebCodecs feasibility review

**Scope:** Read-only review of MediaMTX v1.21.3 source, current official MediaMTX documentation, W3C WebCodecs AVC registration, and MDN browser API documentation. No local files, services, streams or recordings were changed.

### MediaMTX recording/playback findings

- MediaMTX's documented default fMP4 `recordPartDuration` is 1 second. The documentation explicitly describes each fMP4 segment as a concatenation of small MP4 parts and says the last part can be lost on system failure; for MPEG-TS, data is flushed at the configured period. The one-second value is a default, not an approved JudoReplayKit latency target.
- In the v1.21.3 recorder source, the current fMP4 part is accumulated in memory. It is written to the segment file when the part is closed, which occurs when a later sample arrives after the configured part duration has been reached, or when the segment closes. Thus the newest encoded samples are not necessarily present in the file at the instant Replay is requested.
- The fMP4 segment file is created when the first part is closed. The segment's final header duration is written on segment close. The record-store playback code can calculate duration by scanning complete fMP4 parts when the header duration is zero; this means an active segment can potentially be discovered and its already-flushed parts read. It does not make the still-open part available.
- The playback `/get` handler selects segments and muxes the requested interval into an HTTP response at request time. It does not hold a live subscription to the recorder or extend the response with future samples. This agrees with the MediaMTX maintainer's public explanation in issue #5052: the generated MP4 is a snapshot of the available recording when requested; Chrome may appear to continue because it requests again, but the playback service does not provide a continuously growing stream.
- The source review does not establish safe concurrent read/write behaviour under every timing condition. In particular, a read racing with a part being appended must be tested; do not assume that a partially written final box is always harmless.
- Consequence: MediaMTX's archive/playback interface remains a candidate for already-flushed historical material and later retrieval, but it is not by itself a proven immediate live-edge replay buffer. The maximum practical lag cannot be stated from the one-second default alone; it depends on configured part duration, sample arrival, file-write timing and the replay request race.

### WebCodecs / browser feasibility findings

- The W3C AVC registration defines H.264 input to `VideoDecoder` as individual encoded access units (one primary coded picture). It distinguishes AVC format, where codec configuration is supplied as an AVCDecoderConfigurationRecord, from Annex B, where SPS/PPS parameter sets are carried in the stream. This makes per-picture decoding technically plausible, but it does not itself provide transport, demuxing, RTP depacketization, timestamps, or a replay cache.
- MDN documents `VideoDecoder` as available in current desktop Chrome, Edge and Firefox versions, but codec/profile support remains platform-dependent and must be checked using `VideoDecoder.isConfigSupported()` and real camera samples. The API is restricted to secure contexts; localhost is generally treated specially by browsers, while a plain HTTP LAN-IP origin must not be assumed to qualify.
- WebRTC Encoded Transforms (`RTCRtpScriptTransform`) provide a browser-worker path to inspect encoded frames in the WebRTC sender/receiver pipeline and are documented by MDN as broadly available in current browsers. This could avoid decoding the live picture and then trying to recover encoded frames from a rendered `<video>` element. However, compatibility between the actual WebRTC H.264 encoded-frame representation, WebCodecs input requirements, keyframe recovery, and the MediaMTX/browser negotiated codec profile still needs a working PoC.
- MediaMTX supports browser reading through WebRTC and HLS; its documentation states that HLS has higher latency than WebRTC. This is relevant to the live presentation path, but it does not prove that the existing WebRTC browser path exposes encoded frames to a replay cache or meets the live-delay requirements.

### PoC implications — not architecture decisions

1. Test MediaMTX active fMP4 recording at several controlled part durations using disposable recordings. At repeatable points, request a replay interval while the segment is still open. Record the newest media timestamp actually returned, missing-tail duration, errors, and whether a request racing a part write fails or returns truncated data.
2. Test the same camera H.264 samples through a browser WebRTC receiver with an encoded transform, then feed complete access units to WebCodecs. Verify keyframe recovery, SPS/PPS/configuration, monotonic media timestamps, decoded-frame count and correct visual order. Do this separately in current Chrome, Edge and Firefox on the intended Windows/Linux targets.
3. Maintain an explicit bounded decoded-frame ring buffer per camera, with frame timestamps and ownership/lifetime rules for `VideoFrame` objects. Demonstrate that one forward/back action presents exactly the adjacent decoded frame, and that backward stepping never depends on seeking the live stream. This is a proposed test model, not an approved implementation.
4. Verify that the replay decode/cache workload cannot block or restart camera ingest, continuous recording, or the live display. Measure under two simultaneous camera streams and CPU/storage stress.
5. Test origin security separately: localhost, LAN-IP HTTP and a trusted HTTPS origin. Do not assume WebCodecs works on every deployment origin.

### Current assessment

- MediaMTX is a plausible continuous recorder/archive candidate, but its `/get` endpoint is a finite snapshot rather than a live-follow replay mechanism.
- WebRTC Encoded Transforms plus WebCodecs is a plausible browser-side route to an independent encoded/decode buffer. It is not yet proven for the required camera stream formats, browser matrix, timing, frame stepping or isolation.

## 2026-11-15 — WebRTC encoded-frame path and replay-buffer memory review

**Scope:** Follow-up review of the W3C WebRTC Encoded Transform specification, WebCodecs memory model and MDN VideoFrame guidance. Read-only research; no local changes.

### Stronger technical basis for a browser-side encoded-frame tap

- The W3C WebRTC Encoded Transform specification states that a receive-side transform is inserted after the RTP depacketizer and before the browser's decoder. For H.264, the exposed encoded-frame `data` is a series of NAL units in Annex B format; the receiver depacketizer emits frames in encoder output order after RTP reordering.
- The W3C AVC WebCodecs registration says that when `VideoDecoderConfig.description` is absent, H.264 input is interpreted as Annex B. It also defines each `EncodedVideoChunk` as an access unit containing one primary coded picture. These two specifications therefore describe compatible H.264 representations in principle: a WebRTC receive transform can expose Annex-B encoded pictures that a separate WebCodecs decoder may be able to consume.
- This is materially stronger evidence than a generic claim that WebCodecs can decode H.264: it identifies a standards-based location to tap complete depacketized encoded pictures without decoding/re-encoding the main live display. It is still not a working integration. A PoC must verify actual browser frame boundaries, key/delta classification, SPS/PPS availability at keyframes, timestamps, decoder configuration, and that copying frames to a second decoder does not starve the primary WebRTC decoder.
- The transform must pass the original encoded frame through unchanged and in order to the browser's normal receiver decoder. The replay decoder/cache should be independent and bounded. The specification also describes receiver key-frame request support, but whether the selected browser and MediaMTX sender path honours it must be tested.

### Decoded-frame buffer memory risk

- WebCodecs frames can retain substantial system/GPU resources. The WebCodecs specification defines explicit reference management and recommends closing frames when no longer needed; MDN likewise warns that retained VideoFrame objects can consume significant GPU memory.
- A raw decoded-frame ring for both cameras could therefore be expensive. As a planning estimate only, tightly packed 8-bit 4:2:0 video uses about 1.5 bytes per pixel. At 1920x1080, 30 fps and 15 seconds, this is approximately 1.40 GB per camera or 2.80 GB for two cameras. At 30 seconds, it doubles. RGBA storage would be approximately 3.73 GB per camera for the 15-second example. Actual browser/GPU allocation, stride, alignment, hardware surfaces and shared-resource behaviour vary; these are not measured memory requirements.
- This estimate argues against assuming that retaining every decoded frame from both cameras for the full look-back interval is affordable. The PoC should measure actual memory on target PCs and compare at least: (a) a full decoded-frame ring; (b) compressed access-unit ring plus a continuously maintained short decoded window; and (c) compressed ring with decode-on-demand from the preceding keyframe. Any strategy must still demonstrate immediate first-frame availability and exact one-frame stepping without delaying live or recording.
- VideoFrame ownership must be explicit: retain only the frames needed by the replay window, release evicted frames with `close()`, and avoid unnecessary RGBA copies. Rendering may be able to use zero-copy paths such as WebGPU external textures, but this too requires a platform/browser PoC and must not be assumed.

### Updated PoC sequence

1. Establish a working MediaMTX-to-browser WebRTC H.264 receive session on Windows and Linux; record negotiated codec/profile and timestamps.
2. Add a receive-side `RTCRtpScriptTransform` that copies H.264 Annex-B access units into a bounded test ring while passing every original frame through unchanged. Confirm no live-display or ingest regression.
3. Feed a copy of those access units into a separate `VideoDecoder` configured for Annex B; verify continuous decoding and keyframe recovery.
4. Implement a minimal decoded-frame cache and test exact adjacent-frame forward/back navigation, including at buffer wrap and after decoder reset/keyframe loss.
5. Measure memory, CPU, decode queue depth, frame drops and live latency with two simultaneous cameras. Compare the three buffer strategies above.
6. Repeat in current Chrome, Edge and Firefox on target Windows/Linux hardware, plus localhost and intended LAN/HTTPS origins.

### Assessment

- The WebRTC Encoded Transform + WebCodecs combination is now a standards-supported and technically credible PoC candidate for a browser-side independent replay path. It remains **unproven** for the complete JudoReplayKit workflow.
- Key unresolved risks are real-world browser H.264 profile support, keyframe/SPS/PPS handling, timestamps and camera alignment, memory/CPU costs, browser resource pressure, and isolation from the primary live decoder.
- No architecture or technology choice is approved. Status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — WebRTC camera timestamp semantics and cross-camera synchronization

**Scope:** Follow-up review of the W3C WebRTC Encoded Transform specification, WebRTC RTP synchronization requirements, Absolute Capture Time extension documentation, and MediaMTX absolute-timestamp documentation. Read-only research; no local files, services, streams or recordings were changed.

### What the browser can actually expose

- The W3C Encoded Transform metadata distinguishes several different clocks/values: rtpTimestamp, receiveTime, captureTime, and senderCaptureTimeOffset. They must not be treated as interchangeable.
- rtpTimestamp is the RTP sampling-time identifier for that stream. It is suitable for ordering/timing frames within a stream after handling wraparound and clock rate; it is not automatically a shared timebase between two independent camera streams.
- receiveTime for a receiver frame is the local high-resolution time when the last RTP packet needed for that frame was received. It is useful for measuring arrival behaviour, but network jitter and different path delays make it unsuitable as a substitute for camera capture synchronization.
- captureTime is the capture-system time translated into the browser's performance timebase. The W3C specification says it is undefined when the required Absolute Capture Time information is absent and no prior value is available for interpolation. It is therefore conditional, not guaranteed for arbitrary camera sources.
- senderCaptureTimeOffset is needed to relate the sender's NTP clock to the capture system's NTP clock when those clocks differ. Browser metadata availability and actual values must be logged in the PoC rather than assumed.

### What is needed to align two cameras

- RFC 8834 explains RTP synchronization across multiple media sources using a common synchronization context (RTCP CNAME) and RTCP Sender Reports that correlate each stream's RTP clock to a common NTP/system clock. This is a standards-defined synchronization mechanism, but it depends on the source(s) supplying valid correlation information and the streams belonging to a correctly configured synchronization context.
- The Absolute Capture Time RTP header extension carries an NTP capture timestamp and can carry an estimated offset between capture and sender clocks. Its purpose includes synchronization through intermediate systems that terminate RTCP. It is described in WebRTC's extension documentation as an experimental extension; source support and actual propagation must be verified.
- Two independent cameras must not be assumed to share a synchronized capture clock merely because both send RTP, both have RTCP, or their packets arrive at the same PC. If their clocks are not synchronized or their source does not expose capture-time correlation, the system can only establish an arrival-time/ingest-time alignment with a measured uncertainty—not true capture-time alignment.
- MediaMTX's current absolute-timestamp documentation says it can receive and send absolute timestamps over WebRTC and RTSP using RTCP Sender Reports, and that useAbsoluteTimestamp controls whether incoming absolute timestamps are preserved instead of replaced with the server's system timestamp. This is a potentially useful route, but the exact behaviour must be verified against the pinned MediaMTX v1.21.3 source/configuration and the actual chosen camera protocol before relying on it. It is not evidence that a mobile RTMP source provides capture-time timestamps.

### Required PoC checks

1. For each camera, log the encoded-frame rtpTimestamp, receiveTime, captureTime (including whether it is absent), senderCaptureTimeOffset, SSRC, codec/profile, and frame/keyframe type.
2. Capture and inspect RTCP Sender Reports and any Absolute Capture Time RTP header extension at the camera-to-server and server-to-browser boundaries. Record whether MediaMTX preserves or regenerates the timing relationship.
3. Verify whether the two camera sources use a common NTP clock or provide a valid per-source clock offset. If not, report alignment as ingest-time alignment and quantify observed offset/jitter; do not label it capture-time synchronization.
4. Repeat with the actual candidate source protocol. RTMP, RTSP and WebRTC must not be treated as equivalent for absolute timestamp availability.
5. Test drift over a sustained two-camera run, not just initial offset. Record estimated offset, uncertainty and drift over time, and define how a camera reconnect or timestamp discontinuity resets the mapping.

### Assessment

- The browser encoded-frame path has enough standardized metadata to measure more than just packet arrival, but accurate camera capture-time alignment is conditional on timestamp extensions/RTCP clock mapping supplied by the source and preserved through the media server.
- This finding adds a concrete timestamp/clock validation task to the existing WebRTC + WebCodecs PoC. It does not prove the proposed path works with the user's cameras, and it does not approve MediaMTX timestamp settings or any camera protocol.
- No architecture or technology choice is approved. Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — Keyframe recovery requirements for an independent WebCodecs replay decoder

**Scope:** Review of W3C WebRTC Encoded Transform and current MDN documentation for receiver-side keyframe requests. Read-only research; no local changes.

### Findings

- H.264 delta pictures depend on earlier reference pictures. A separate replay decoder cannot reliably start at an arbitrary access unit; it needs a decodable keyframe/IDR and the relevant parameter sets (SPS/PPS), followed by the dependent pictures in decode order.
- The WebRTC Encoded Transform API exposes a receiver-side sendKeyFrameRequest() method. MDN marks it Baseline 2025 / newly available since October 2025 in current browsers. It can request that the remote sender emit a keyframe when the receiver cannot decode without one.
- Critical limitation: the browser may decide a keyframe request is unnecessary. In that case the returned promise still fulfils even though no request was actually sent. A fulfilled promise is therefore not proof that a keyframe was requested, transmitted, received, or decoded.
- Even if the browser sends the request, the full path must work: browser receiver -> RTCP feedback/PLI or equivalent -> MediaMTX -> original camera/encoder -> new keyframe -> browser receiver transform. The API documentation does not prove that this exact MediaMTX version and camera source will honour the request.
- Periodically requesting keyframes can improve recovery/seekability but may increase bitrate and encoder load. The PoC must measure the effect and must not add an aggressive PLI loop that harms the live stream or recording.

### Required PoC tests

1. Start the receiver transform before the first incoming video frame and record time to first usable IDR/SPS/PPS and first successful independent WebCodecs decode.
2. Deliberately reset the replay decoder and request a keyframe. Verify that an actual new IDR reaches the transform and that the separate decoder recovers; do not count promise fulfilment as success.
3. Repeat after packet loss, a camera reconnect, a buffer wrap, and a deliberately discarded/corrupt access unit.
4. Test whether MediaMTX v1.21.3 forwards the relevant RTCP feedback to the publishing camera, and whether the actual camera encoder reacts. Record request-to-IDR latency.
5. Measure bitrate, encoder load, live latency and recording continuity with keyframe requests enabled versus disabled.
6. If keyframe requests are unsupported or unreliable, the replay cache must remain continuously primed from the start of the stream and preserve a valid prior keyframe plus all dependent access units needed for decoding. Recovery after cache loss must be reported as unavailable until a valid keyframe arrives.

### Assessment

- Receiver-side keyframe requesting is a real API capability and improves the technical plausibility of decoder recovery, but it is not a deterministic instant-replay guarantee.
- The independent replay decoder still needs a bounded, continuously maintained decodable history and an explicit recovery state machine. It must never silently display a stale or undecodable frame as if it were current.
- This adds a high-priority recovery test to the WebRTC + WebCodecs PoC. No architecture is selected; overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — MediaMTX v1.21.3 source periodically requests keyframes from WebRTC publishers

### Verified source behaviour

- In MediaMTX v1.21.3, internal/protocols/webrtc/inbound_track.go defines keyFrameInterval as 2 seconds.
- When an incoming WebRTC video track starts, InboundTrack.start() starts a ticker at that interval and writes an RTCP Picture Loss Indication (PLI) to the inbound WebRTC receiver's RTCP channel, identifying the publisher track SSRC.

- It does not apply to a camera source publishing through RTMP; RTMP does not carry this WebRTC RTCP feedback path. The actual camera-to-MediaMTX protocol is therefore decisive.
- The two-second interval is an implementation detail of MediaMTX v1.21.3, not a JudoReplayKit requirement or a measured maximum recovery time. It must be verified with the selected source and may have bitrate/encoder-load implications.
- Since MediaMTX sends periodic PLIs independently of the replay UI, this mechanism may keep the incoming WebRTC stream's keyframe cadence healthy without the replay client needing to forward its own requests. However, the replay decoder must still maintain its own valid compressed/decode history and handle missing or delayed keyframes explicitly.

1. Use the actual candidate camera source protocol and record every PLI emitted by MediaMTX, plus the corresponding IDR/SPS/PPS arrival at the server and browser receiver.

### Assessment

- This source inspection materially improves the WebRTC ingest candidate: MediaMTX v1.21.3 already sends periodic PLI requests to WebRTC publishers every two seconds.
- It does not remove the need for the keyframe recovery PoC and does not help an RTMP ingest path through RTCP.

## 2026-11-15 — MediaMTX WebRTC fan-out and independent reader behaviour: source-level review

### Findings

- MediaMTX's WebRTC server handles each reader as a separate WebRTC peer connection. A reader has its own outbound tracks and RTP/RTCP sender state; the server fans out the path's encoded media to readers rather than sharing a single browser decoder.

- A browser-side independent WebCodecs decoder fed by a receiver transform would be downstream of the ordinary WebRTC receiver. The original encoded frame must still pass unchanged to the normal browser decoder; the replay branch must use its own bounded queues, decoder, frame ownership and rendering surface. MediaMTX's reader fan-out alone does not provide this independent replay branch.

- Separate peer connections do not mean separate camera encoders. A single publishing camera/stream can still be the shared source for both live and replay readers.
- Multiple readers can increase server packet forwarding, network egress and browser decode work. A separate replay decoder on the same PC competes for CPU/GPU/memory bandwidth with live presentation and recording even if its software queues are independent.

- RTMP camera ingest does not gain RTCP PLI merely because the browser reads the stream over WebRTC. The source protocol remains a gating decision for this recovery mechanism.
- Source review did not establish whether every codec/profile/packetization mode can be passed through to all supported browsers, nor did it measure performance under two cameras and simultaneous live/replay decode.

1. Run one WebRTC publisher with two simultaneous MediaMTX readers: one normal live view and one replay/test reader. Confirm timestamps, packet continuity, and that pausing/seeking the replay reader does not affect the live reader.

5. Test publisher reconnect and reader reconnect separately; ensure one reader's failure does not tear down the publisher or other reader.

- MediaMTX's per-reader peer-connection model is compatible with isolating reader control state, but it is not a performance or live-continuity guarantee.

## 2026-11-15 — WebCodecs decoder queue, frame lifetime and presentation-order constraints

**Scope:** Review of the current W3C WebCodecs specification and MDN implementation guidance. No local files or running services were changed.

### Findings

- WebCodecs VideoDecoder is asynchronous. decode() enqueues work; output VideoFrames arrive later through the output callback. The application must not assume a decode() call means the corresponding frame is immediately available.
- The decoder's decodeQueueSize exposes pending decode requests. It must be monitored and bounded; an unbounded input queue can accumulate work and latency. The replay path needs explicit backpressure and a policy for overload that never blocks or delays the original WebRTC live path.
- The W3C specification requires VideoDecoder outputs in presentation order. Implementations may internally reorder decoded pictures to achieve this. This is important for H.264 streams containing B-frames: the encoded access units may be supplied in decode order, while decoded output is delivered in display/presentation order.
- EncodedVideoChunk.timestamp is a presentation timestamp in microseconds, and WebCodecs carries it through to the corresponding VideoFrame. The timestamp origin is media-defined and not guaranteed to be shared across separate streams. RTP timestamp metadata is a separate 90 kHz stream-clock value; it must be unwrapped and mapped deliberately rather than copied blindly as if it were already a microsecond presentation timestamp.
- RTCEncodedVideoFrame metadata includes RTP timestamp and SSRC/synchronization source. RTP timestamp identifies the sampling instant in that stream; it is not itself a shared cross-camera wall clock. The browser transform's receiveTime and captureTime have different semantics as documented in the earlier timestamp entry.
- VideoDecoder.flush() is not a periodic "make frames appear now" operation. The WebCodecs specification sets the decoder's key-chunk-required state when flush() is called. Subsequent decode input must begin with a key chunk. Calling flush() during normal continuous replay-buffer decoding can therefore force a keyframe restart and disrupt the rolling decoder.
- reset() synchronously aborts pending work and clears queued control messages; it is not a harmless pause or seek. After reset/reconfigure, decoding must restart from a keyframe. A decoder error closes the decoder; recovery requires a new decoder instance configured again and a valid keyframe.
- VideoFrame resources are not ordinary small JS objects. W3C and MDN advise explicitly closing frames when no longer needed; retaining many frames can exhaust GPU/media resources and stall or crash the application. A frame cache therefore needs strict count/age/byte limits, deterministic ownership, and close() on eviction. Clone() shares the underlying media resource rather than creating a free independent copy.
- MDN currently warns that VideoDecoder is not Baseline across every major browser and requires a secure context. Current compatibility data reports desktop support in modern Chrome/Edge and Firefox, but actual codec/profile support and platform acceleration vary. Runtime feature detection and VideoDecoder.isConfigSupported() are necessary, followed by decoding real camera samples. The LAN deployment must use a secure context such as HTTPS or a browser-trusted localhost origin; plain HTTP LAN-IP must not be assumed to work.

### Consequences for exact frame stepping

- The UI must step through decoded VideoFrames in presentation order, not by incrementing an RTP timestamp or selecting every Nth encoded access unit.
- Each displayed decoded frame needs a stable sequence ID and media timestamp. Step-forward/backward moves exactly one adjacent cached decoded frame. If that frame is not present, the UI must show that the requested frame is unavailable while the decoder catches up; it must not silently jump to live.
- The replay decoder should remain continuously primed and should not call flush() or reset() merely because the user pauses, steps, or opens/closes the replay overlay.
- The live WebRTC receiver must continue to pass every encoded frame unchanged and in order. The replay branch should have its own bounded copy/queue and a drop/recovery policy; replay overload must never back-pressure the receiver's live pass-through.
- Retaining the full 15-second decoded history for two 1080p/30 streams is likely to be resource-intensive. Compare bounded rolling decoded windows, compressed access-unit history plus a warm decoder, and decode-on-demand from a prior keyframe. No strategy is proven; immediate first-frame access and exact reverse stepping remain mandatory test outcomes.

### Required PoC checks

1. Use actual H.264 camera access units with and without B-frames; verify input order, RTP timestamps, EncodedVideoChunk timestamps and decoded VideoFrame output order.
2. Verify correct 90 kHz RTP timestamp unwrapping and conversion to a monotonic media timeline in microseconds, including wraparound, reconnect and timestamp discontinuities.
3. Keep a decoder continuously running; confirm pause/step operations do not call flush() or reset() and do not cause a keyframe-only restart.
4. Deliberately overload the replay decoder and measure queue depth, dropped replay frames, live latency, packet loss and recording continuity. Verify the live branch is unaffected.
5. Measure actual VideoFrame resource usage and release behaviour on Windows and Linux; test two cameras and the maximum configured replay history.
6. Test VideoDecoder.isConfigSupported() and real decode for the exact H.264 profile, level, resolution, bit depth and chroma format from each candidate camera in every target browser.
7. Test HTTPS and the intended localhost/LAN access model on Windows and Linux.

### Assessment

- WebCodecs provides the required decoded-frame presentation ordering and explicit decoder lifecycle controls, but these do not automatically create a safe instant-replay cache.
- The most important implementation hazard found here is treating flush()/reset() as normal replay controls. They alter decoder state and can force a new keyframe requirement.
- A continuously primed, bounded, independently managed decoder/cache is still the strongest browser PoC candidate, but memory, codec compatibility, frame timestamp mapping and live isolation must be measured before any architecture decision.
- Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

### Verified pipeline placement

- The W3C specification places a receiver-side encoded transform between the RTP depacketizer and the browser's normal media decoder.
- The depacketizer's encoded frame is passed through the transform algorithm and then to the associated decoder. Therefore, if JudoReplayKit adds a receiver transform to the same PeerConnection used for visible live video, its transform code executes on the live receive/decode path.
- The W3C specification explicitly states that stream backpressure is disabled for WebRTC encoded transforms. This is intentional because WebRTC favours low latency over reliable buffering. Applications must not assume a slow replay-copy operation will safely backpressure the producer; overload may instead result in queued work, dropped frames or latency depending on implementation behaviour.
- The receiver transform can be attached in the track event before the first full encoded frame, but it still becomes part of the path that feeds the browser's ordinary decoder.

### Architectural consequence

A single PeerConnection with a receiver transform is efficient in network terms, but it does not provide strict live-path isolation: the transform must inspect/copy the encoded frame before passing it to the live decoder. A bounded, fast, synchronous copy may prove harmless, but that is a measured property, not a guarantee.

A separate WebRTC PeerConnection/reader dedicated to replay is an alternative:
- Keep the visible live PeerConnection free of application transform code.
- Attach the receiver transform and replay ring only to the replay PeerConnection.
- This increases MediaMTX reader count and network egress, and may add another browser decode path depending on how the receiver track is handled.
- It does not eliminate competition for browser CPU, GPU, memory or network bandwidth. It only separates the live receive/decode pipeline from replay-specific JavaScript work.
- The replay reader must remain continuously connected and maintain its own bounded decodable history; connecting only after Replay is pressed would reintroduce keyframe/GOP wait time.
- MediaMTX's separate-reader model and periodic publisher PLI are relevant, but do not guarantee replay readiness or resource isolation.

### Required comparison PoC

A. Single receiver:
1. One WebRTC PeerConnection for visible live video.
2. Receiver transform copies access units into a bounded replay ring and immediately passes the original encoded frame unchanged to the normal decoder.
3. Measure transform execution time, copy time, live glass-to-glass latency, dropped frames, jitter-buffer behaviour and CPU/GPU under two cameras.

B. Separate replay receiver:
1. One unmodified PeerConnection for visible live video.
2. A second PeerConnection per camera for replay buffering, with receiver transform and independent replay decoder/cache.
3. Measure added server/network load, whether the hidden replay receiver triggers a second native decode, total CPU/GPU/memory, and live latency.
4. Pause, step, reset and overload replay while verifying that the live PeerConnection and visible stream remain unaffected.

C. Compare both with replay idle, active, overloaded and during reconnects. A result passes only if live latency/continuity remain within the test's pre-agreed tolerance and recording is unchanged.

### Assessment

- The single-transform design cannot be described as "no impact on live" before measurement because it inserts application work directly into the live receive pipeline.
- The separate replay receiver is a more credible isolation candidate for the user's highest-priority requirement, at the cost of extra bandwidth and decode/resource use.
- Both designs remain PoC candidates. Do not select one before measuring two-camera operation on the target Windows/Linux PC.
- Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — MediaMTX v1.21.3 gives each WebRTC reader an independent outbound queue

**Scope:** Direct inspection of the exact v1.21.3 source for WebRTC sessions, stream fan-out and reader queues. No local services, streams or recordings were changed.

### Verified source behaviour

- Each MediaMTX WebRTC read session calls PathManager.AddReader(), creates its own internal WebRTC PeerConnection, registers a distinct stream.Reader, and adds that reader to the shared stream.
- Stream.AddReader() starts a separate ring buffer for that reader and registers that reader's callbacks with the stream's media formats.
- Each Reader owns its own ring buffer and worker goroutine. When the buffer cannot accept another callback, Reader.push() increments an outbound-discard counter instead of blocking the shared stream writer.
- Stream.RemoveReader() unregisters only that reader's callbacks, removes that reader from the reader set, and closes its own queue.
- Therefore a slow replay reader has a separate MediaMTX queue from the live reader. Queue overflow is recorded as discarded frames on that reader rather than being allowed to block the shared stream writer through that reader's queue.
- This is a meaningful server-side isolation mechanism. It is not a guarantee that replay never loses frames: a slow replay reader can discard frames, and losing a reference frame may make following H.264 delta frames undecodable until the next usable keyframe.
- The separate reader still adds packet fan-out and network egress. The server maintains a separate PeerConnection/RTP sender for the reader; it does not create a separate camera encoder. Browser-side CPU/GPU/memory competition also remains.

### Consequences for JudoReplayKit

- A second, continuously connected MediaMTX WebRTC reader for replay is now better supported by source evidence than a generic "second connection" assumption: MediaMTX explicitly maintains per-reader queues and drops only the slow reader's queued work when that queue is full.
- This makes it a stronger candidate for protecting the visible live receiver from replay transform/copy work than putting the transform on the live receiver itself.
- The replay application must monitor server reader-discard metrics/logs and its own sequence/timestamp continuity. Any gap that breaks the decode dependency chain must mark the replay cache as discontinuous and wait for a valid keyframe before claiming frame-accurate stepping.
- The replay reader should not be connected only when Replay is pressed; it must be continuously primed, otherwise connection setup and GOP/keyframe wait would add delay.
- The exact writeQueueSize setting and its effective frame capacity must be measured/configured carefully. A large queue can hide lag and increase memory/latency; a small queue can discard replay frames under bursts. Do not infer a time duration directly from queue length without measuring frame rate and callback behaviour.

### Required PoC checks

1. Establish one MediaMTX publisher and two independent WebRTC readers (live and replay).
2. Deliberately stall the replay reader until its queue overflows; verify MediaMTX records replay-reader frame discards while live remains continuous and its latency does not increase.
3. Verify that replay detects sequence/timestamp gaps, invalidates the affected decode dependency chain, and recovers only at a valid keyframe.
4. Measure server CPU, memory, outbound bandwidth and queue occupancy with two cameras and two readers per camera.
5. Test reconnect/removal of the replay reader while live remains connected; verify no publisher restart, live renegotiation or recording interruption.
6. Measure the chosen queue size against real frame rates, bursts and expected replay duration; do not rely on default values without testing.

### Assessment

- MediaMTX's independent reader queues provide concrete source-level support for reader isolation and non-blocking overflow handling.
- This strengthens the separate replay-reader PoC candidate. It does not prove end-to-end no-impact, because shared server resources, network egress and browser resource contention remain.
- The separate replay-reader design is now the leading isolation experiment to compare against the single-transform design, but it is not selected or approved.
- Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — MediaMTX reader queue is a transient pending-work queue, not a replay time-shift buffer

**Scope:** Exact v1.21.3 source inspection of global configuration defaults and per-reader queue implementation. No local configuration was changed.

### Verified details

- MediaMTX v1.21.3 sets global WriteQueueSize to 512 by default.
- Each stream.Reader creates a ring buffer with that configured capacity. The ring buffer stores pending callback work for that reader; it is not a timestamp-indexed history of previously delivered video and it is not a 15-second replay store.
- A queue-full condition causes that reader's pending callback to be discarded and increments the reader's outbound-frame-discard counter. The application must treat this as potential media discontinuity, not as a harmless drop.
- The configured value 512 is a count of pending queue entries, not a guaranteed number of seconds. It must not be described as a replay buffer or converted to a time duration without validating the exact callback granularity and sustained input rate.
- Increasing the queue size can absorb longer temporary stalls but can also retain more pending work and increase replay lag/memory. Decreasing it can cause earlier frame loss. The default is not automatically appropriate for a referee replay workload.

### Consequence

The separate replay WebRTC reader provides a useful isolation boundary, but JudoReplayKit still needs its own bounded, timestamped encoded-access-unit ring and decoder/frame cache. MediaMTX's reader queue only transports pending work from the shared stream to each reader; it does not supply the look-back history.

### Required PoC checks

1. Measure the actual number of reader queue entries per second for the intended H.264 source and confirm whether one entry corresponds to one access unit or another unit of work.
2. Stall only the replay reader and record queue occupancy, discard counter, recovery time and live-reader latency.
3. Tune queue size against measured transient stalls, but keep the actual replay history in a separate application-owned buffer with explicit age/byte limits.
4. Verify that queue overflow invalidates the replay decoder dependency chain and is surfaced to the user until a valid keyframe and continuous decode are restored.

## 2026-11-15 — MediaMTX reader queue capacity is shared across a reader session, not a video-frame budget

**Scope:** Exact v1.21.3 source inspection of `internal/stream/reader.go` and `internal/stream/stream.go`. Source-level finding only; no runtime test or local changes.

### Verified details

- Each `Reader` owns one `ringbuffer.RingBuffer` and one worker goroutine. The ring buffer stores callback work (`func() error`), not a timestamped media history.
- `Stream.AddReader()` assigns the stream-wide `WriteQueueSize` to the reader once, starts that one queue, then registers callbacks for every media/format that the reader requested.
- Consequently, the queue capacity is shared by all registered tracks/formats within that reader session. It is not a separate 512-entry video queue per track, nor a 512-frame guarantee. Audio and video callback work can both consume the same reader queue capacity.
- On overflow, the reader increments `outboundFramesDiscarded` and logs that the reader is too slow. This counter is useful but must not be treated as an exact count of only visible video frames without confirming the callback path and track mix.
- The queue size is configured at stream level and copied into each Reader at registration. Changing the configured value therefore affects the capacity of each subsequently created reader, not the replay-history duration.

### Consequences for JudoReplayKit

- Do not convert `writeQueueSize: 512` into seconds or video frames. The effective capacity depends on how MediaMTX enqueues units/callbacks for the actual audio/video tracks and the source frame cadence.
- The PoC must measure queue overflow with the actual source and track combination. Record reader-discard counter deltas, per-track callback rates if instrumented, browser decoded-frame continuity, and live latency.
- If a replay reader is stalled, audio callbacks may contribute to the same queue pressure as video callbacks. Test with audio enabled and disabled as separate cases; do not tune based only on video-only synthetic input.
- Keep the application's own replay history separate from this transient server queue.

## 2026-11-15 — MediaMTX prepends its stored H.264 parameter-set pair at random-access units

**Scope:** Exact v1.21.3 source inspection of `internal/stream/unit_remuxer.go` and `internal/stream/format_updater.go`. Source-level finding only; no runtime test and no local changes.

### Verified behaviour

- The H.264 unit remuxer identifies random-access access units. When its output format has both an SPS and a PPS stored, it prepends that pair to the random-access access unit before passing it to readers.
- The remuxer removes in-band SPS/PPS NAL units from the outgoing access unit and uses the format's stored pair instead. This helps a reader that joins before the next supported random-access unit: the next such unit can carry the currently stored SPS/PPS in-band.
- The H.264 format updater scans incoming access units and stores a changed SPS and PPS in the format description. The implementation stores one SPS field and one PPS field, replacing the stored value when a different one is encountered; it does not maintain a map keyed by parameter-set ID.
- Therefore this mechanism does not provide the previous GOP to a late reader and does not remove GOP wait. It only improves decoder initialization when a subsequent random-access access unit arrives and the stored parameter-set pair matches the slices.
- This single-pair behaviour is consistent with the unresolved multiple-PPS compatibility concern documented above from upstream issue #6269. A stream whose slices reference a different PPS than the last stored one may still be undecodable after remuxing.

### Consequence for the replay PoC

- Measure the first random-access access unit delivered to a cold reader and confirm that its prepended SPS/PPS actually match the PPS IDs referenced by its slices.
- For a continuously connected warm replay reader, retain the complete decoder dependency chain from a valid random-access point. Do not assume a newly opened decoder can start at an arbitrary P-frame or that MediaMTX's stored pair covers multi-PPS streams.
- Keep the single-PPS case and multiple-PPS case as separate source compatibility tests.

## 2026-11-15 — Warm H.264 replay buffer: compressed history plus bounded decoded-frame cache

**Scope:** Design analysis based on W3C WebCodecs and WebRTC Encoded Transform specifications and MDN guidance. No runtime PoC was run; no architecture is selected and no local files/services/configurations were touched.

### Core finding

A compressed H.264 access-unit ring is memory-efficient, but it cannot independently provide an immediately displayable arbitrary historical frame. H.264 decoding must begin at a valid key/random-access chunk with the required parameter sets and then consume the dependent access units in decode order. WebCodecs outputs decoded frames in presentation order. A VideoDecoder that has been reset or recreated requires a new key chunk; VideoFrame resources must be explicitly closed when evicted, and decodeQueueSize must be bounded.

### Memory estimates

Assumptions: 30 fps, 15 seconds, tightly packed 8-bit 4:2:0/NV12 (1.5 bytes per pixel), decimal MB/GB. These are raw image-payload estimates only; actual GPU/system allocation, row alignment, copies and metadata may increase usage.

- 1920x1080: 3,110,400 bytes/frame x 450 frames = 1.40 GB per camera; 2.80 GB for two cameras.
- 1280x720: 1,382,400 bytes/frame x 450 frames = 0.62 GB per camera; 1.24 GB for two cameras.
- 8 Mbit/s compressed H.264 for 15 seconds = 15 MB per camera (30 MB for two), before ring metadata/overhead. Actual bitrate and GOP affect this.
- Full decoded 30-second history doubles the 15-second figures. At 60 fps, decoded cache estimates double again.

### Candidate buffer model for PoC (not architecture approval)

1. Keep a permanently connected, dedicated replay receiver per camera. The normal live-view PeerConnection remains free of application transforms where possible.
2. Copy encoded H.264 access units into a fixed-size, time- and byte-bounded circular buffer. Store monotonic presentation/decode timing, key/random-access markers, SPS/PPS identity/version, source/connection epoch and discontinuity markers. Evict only at a safe random-access boundary; never leave a retained dependent access unit without its required preceding decode chain.
3. Run a dedicated warm VideoDecoder continuously from that replay receiver. Maintain a bounded decoded-frame cache for the configured replay horizon if the target hardware can sustain it. This is the only straightforward way to guarantee an already-decoded frame at arbitrary points across the whole horizon.
4. Keep the compressed ring as the lower-memory recovery/history layer. If the full decoded cache is too expensive, test a shorter decoded hot window plus compressed history and measure cold pre-roll decode latency from the preceding keyframe. This fallback must be labelled as a latency trade-off; it does not meet instant arbitrary seek unless the measured pre-roll is acceptably fast.
5. Bound every queue and ring. If decode falls behind, record the gap and recover at the next valid keyframe; do not let replay work block or backpressure live ingest/recording. The W3C WebRTC Encoded Transform spec explicitly disables Streams backpressure because WebRTC prioritizes low latency, so an application transform must not assume that a slow worker safely pauses media production.
6. On eviction, call VideoFrame.close() exactly once for each owned frame. Avoid unnecessary clone/copy operations. Track decoded-frame count, bytes where measurable, decodeQueueSize, decode throughput, keyframe recovery, dropped access units and browser/GPU memory.

### Important trade-off

- Full-horizon decoded cache: strongest candidate for instant first-frame display and exact frame stepping, but potentially very high memory/GPU cost (especially two 1080p cameras).
- Compressed ring + short decoded cache: much lower memory, but historical positions outside the decoded hot window require decoding from a prior keyframe; button-to-first-frame latency is therefore not guaranteed to be immediate.
- A low-resolution decoded cache with full-resolution compressed history may improve responsiveness but cannot silently substitute lower-resolution replay if the referee must inspect full detail. Any quality trade-off must be explicit and tested.

### PoC acceptance measurements

- Two cameras at target resolution/fps/bitrate, each with a permanently warm replay receiver and decoder.
- Measure memory/GPU allocation over time and verify strict upper bounds; stress with 5/15/30-second retention and two simultaneous replay operations.
- Verify every retained decoded frame has correct presentation timestamp and exact adjacent frame stepping in both directions, including across IDR/GOP boundaries.
- Verify ring eviction always leaves a decodable start point and matching SPS/PPS; test multiple PPS, parameter-set changes, reconnects, missing/corrupt access units and long GOPs.
- Measure replay-button-to-first-displayed-frame separately for positions inside and outside the decoded hot window. Do not call a WebRTC connection established or an encoded chunk received a successful replay.
- Measure live-view latency, recording continuity, replay decode backlog, dropped units and CPU/GPU independently. Any live degradation is a PoC failure for the isolation requirement.

### Evidence

- W3C WebCodecs: https://www.w3.org/TR/webcodecs/
- W3C WebRTC Encoded Transform (backpressure disabled): https://www.w3.org/TR/webrtc-encoded-transform/
- MDN WebCodecs usage and VideoFrame resource management: https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API/Using_the_WebCodecs_API

### Assessment

The strongest next experiment is a continuously warm replay decoder with a bounded decoded-frame cache plus a compressed access-unit ring. This is a candidate to test, not a selected architecture. If full-horizon decoded caching is too expensive, the hybrid fallback must be judged against measured first-frame latency, not assumed to be instant. ## 2026-11-15 — Hardware decoding: Windows/Linux feasibility and VideoFrame resource retention

**Scope:** Review of the current W3C WebCodecs specification, MDN API documentation, Microsoft Edge H.264 playback guidance, and Chromium platform decoder documentation. Research only; no runtime PoC, local changes, or architecture decision.

### Verified findings

- WebCodecs `VideoDecoderConfig.hardwareAcceleration` accepts `no-preference`, `prefer-hardware`, and `prefer-software`. These are hints, not guarantees; a user agent may ignore them. The W3C specification notes that hardware decoding can reduce CPU load and improve throughput consistency, but may have higher startup latency and can be less robust with malformed or non-conforming bitstreams.
- `VideoDecoder.isConfigSupported()` reports whether the supplied decoder configuration is supported. It does not identify the actual decoder backend selected at runtime. `MediaCapabilities.decodingInfo()` reports `supported`, `smooth`, and `powerEfficient`, but those signals must not be treated as direct proof that a specific VideoDecoder instance is using a hardware backend.

Those resources may occupy system memory, GPU memory, or decoder/system resources; they remain alive while referenced. `close()` releases that reference, while `clone()` creates another object referencing the same underlying resource rather than necessarily copying pixels. Transferring a VideoFrame moves its resource reference to the destination object and closes the source object.
- Consequently, hardware decoding does not make a retained decoded-frame ring free or automatically small. Retaining VideoFrames may pin scarce GPU/decoder surfaces or other resources even if the pixel data is not copied into ordinary JavaScript memory. The actual allocation strategy is implementation-specific and must be measured on target systems. 5. Explicitly test long-lived retained VideoFrames and eviction. Measure whether keeping decoded frames starves the decoder's output-surface pool, increases memory pressure, or stalls new output. Ensure every owned frame is closed exactly once when evicted. Compare keeping native VideoFrames against copying selected frames into a separately bounded representation; any copy cost must be measured.
6. Keep software decoding as a tested fallback, but do not assume it will meet the two-camera load or instant-replay latency requirement. Hardware acceleration is a performance option, not a substitute for bounded buffers, keyframe recovery, or replay/live isolation.
7. The Linux PoC must identify the exact distro, browser package/build, GPU model, kernel, VA-API driver and supported H.264 profiles. A result on one Linux configuration does not establish general Linux support.

Hardware decoding is a credible way to reduce CPU pressure, particularly on Windows, but it does not resolve the decoded-frame retention cost and may introduce constrained GPU/decoder-surface pools. ## 2026-11-15 — Decoded-frame cache alternatives: retained VideoFrames versus copied pixel buffers

**Scope:** Review of current W3C WebCodecs memory, VideoFrame copy and transfer semantics, and Chromium Linux hardware-decoding diagnostics. Research only; no runtime PoC, local changes, or architecture decision.

### Verified findings

- The current W3C WebCodecs specification explicitly defines codec system resources to include CPU memory, GPU memory and exclusive handles to decoding/encoding hardware. Such resources may be quickly exhausted and should be released when no longer needed.
- A VideoFrame holds a reference to a media resource. `clone()` creates another VideoFrame object referencing the same media resource; it is not a deep pixel copy. `close()` releases that object's resource reference. Transferring a VideoFrame moves the reference to the receiving realm and closes the source object; it does not promise a pixel copy or release the resource while the destination still retains it.
- `VideoFrame.copyTo(destination)` asynchronously copies pixel planes into an application-provided ArrayBuffer/TypedArray/DataView. This can make the retained cache independent of the decoder's original VideoFrame resource, after which the VideoFrame can be closed. However, the copy consumes memory bandwidth and a separate destination allocation; it does not eliminate the pixel-data storage cost. Destination format/layout and actual allocation size must be measured on each implementation.
- The WebCodecs specification warns that decoded media can occupy large amounts of memory and encourages prompt `close()` calls. It also explicitly warns that GPU memory and exclusive codec hardware handles are among the system resources that can be exhausted.
- `VideoDecoder.isConfigSupported()` returns a `supported` boolean and the recognized configuration. The WebCodecs `VideoDecoderSupport` dictionary does not report the selected hardware/software backend. Decoder backend must be verified separately with browser/platform diagnostics and measured telemetry.
- The WebCodecs hardware acceleration options remain hints. The W3C specification notes higher startup latency can occur with hardware decode, throughput may be more consistent and CPU load generally lower; support may be restricted by codec profile/device, and hardware decoders may be less robust to malformed or non-conforming input.
- Chromium's Linux VA-API document says Linux VA-API is not supported by default in the documented configuration and may work on certain configurations without guarantees. It documents `chrome://media-internals` and the `video_decoder` property (`GpuVideoDecoder`) as a way to verify the accelerated decoder backend for a playing video. This diagnostic is useful for Chromium media playback, but a separate WebCodecs VideoDecoder instance must still be correlated to the correct media-internals entry or otherwise instrumented; do not assume a normal `<video>` entry proves the WebCodecs decoder backend.

### Buffer alternatives to compare in the JudoReplayKit PoC

**A. Retain decoded VideoFrames directly**
- Lowest explicit application-side copy cost and potentially best GPU-resident display path.
- Can retain decoder/GPU surfaces and other scarce system resources for the whole retention window. A long ring can starve decoder output or increase GPU memory pressure; actual pool limits are implementation-specific and must be measured.
- Requires strict ownership, bounded count/time, and exactly one `close()` per owned frame on eviction.

**B. Copy decoded frames into a bounded CPU pixel ring**
- Use `VideoFrame.copyTo()` into application-owned buffers, then close the original VideoFrame promptly. This may release decoder/GPU surface references earlier and make cache lifetime independent of the hardware decoder.
- Pixel storage remains large and copies add memory bandwidth/latency. At full resolution the cache may still consume approximately the raw-frame payload budget calculated earlier, depending on chosen pixel format/stride; actual `allocationSize()` and destination bytes must be recorded rather than assuming tightly packed NV12.
- Rendering may require upload/conversion back to a GPU surface, adding cost when displaying a selected historical frame. Test first-frame display and step responsiveness, not just copy throughput.

**C. Compressed history plus short decoded hot window**
- Keep the longer H.264 access-unit ring compressed and decode continuously into only a short decoded window. This minimizes decoded storage and limits retained VideoFrame resources.
- A requested position outside the hot window must be decoded from the preceding valid keyframe. This can add variable delay and does not guarantee immediate first-frame display for the entire history.
- This is a useful fallback only if measured keyframe pre-roll is acceptably fast for the referee workflow; it must not be described as instant arbitrary replay without results.

### Required measurements and test design

1. Run the same real camera bitstream through A, B and C on each target OS/browser/GPU. Test 720p and target 1080p, actual frame rate, two cameras, and two simultaneous replay operations.
2. For A, measure active VideoFrame count, GPU dedicated/shared memory, system memory, decoder output cadence, stalls and errors as retention grows. Stress retention beyond the expected steady-state and confirm prompt recovery after eviction.
3. For B, record `VideoFrame.allocationSize()` for the selected copy format, actual destination bytes, copy completion latency, memory bandwidth/CPU, GPU memory before/after `close()`, and selected-frame render/upload latency. Compare source frame formats and alignment.
4. For C, measure replay-button-to-first-displayed-frame at random positions both inside and outside the hot window, including worst-case distance from preceding IDR, long GOP, camera reconnect and decoder recovery.
5. For every design, verify exact adjacent frame stepping in both directions, presentation timestamps, no duplicate/missing frames, and continued live/recording operation. Bound encoded ring, decoded cache, copy queues and decoder queue independently.
6. Do not infer actual hardware decoding from `isConfigSupported()` or a requested `prefer-hardware` hint. Record backend evidence from platform diagnostics where available and cross-check CPU/GPU telemetry during the WebCodecs PoC.

### Assessment

Three different resource models now need direct comparison: retaining decoder-backed frames, copying frames into a CPU-owned pixel ring, and keeping only a short decoded hot window with compressed history. Copying may release GPU/decoder references sooner but does not reduce the fundamental raw-pixel storage requirement; the hybrid reduces memory but can reintroduce seek latency. No option is selected. Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — WebGPU replay rendering: external textures versus persistent GPU frame cache

**Scope:** Review of current W3C WebGPU/WebCodecs specifications and MDN API documentation. Research only; no runtime PoC, local changes, or architecture decision.

### Verified findings

- `GPUDevice.importExternalTexture({source: VideoFrame})` creates a sampleable `GPUExternalTexture` snapshot. The WebGPU specification says it may be implemented without copying the source, but this is implementation-dependent; ownership may be shared with the decoder or exclusive. It is not a guaranteed zero-copy contract.
- A `GPUExternalTexture` created from a `VideoFrame` remains valid only while the source VideoFrame remains open. Closing the VideoFrame expires the external texture. If the external texture remains referenced, it can keep the VideoFrame and its media resource alive. The WebGPU specification explicitly warns that failing to close VideoFrames can stall the decoder.
- `GPUExternalTexture` is a sampleable external-video texture, not a general persistent application-owned pixel store. It is intended for GPU sampling/rendering; its internal representation is implementation-defined and may contain multiple planes and color-conversion metadata.
- `GPUQueue.copyExternalImageToTexture()` accepts a VideoFrame source and copies a snapshot into an application-created GPUTexture. This creates a persistent application-owned GPU copy that can outlive the source VideoFrame, allowing the original decoder-backed VideoFrame to be closed after the copy has completed/been safely queued according to API semantics. The GPUTexture still consumes GPU memory; this is a transfer of resource ownership, not elimination of storage cost.
- MDN currently marks `GPUDevice.importExternalTexture()` and `GPUQueue.copyExternalImageToTexture()` as limited availability and secure-context-only. WebGPU must therefore be an optional fast path with feature detection and a non-WebGPU fallback, not a mandatory browser baseline.
- WebGPU's external texture and copy APIs can be exposed in workers on supporting implementations. Chrome's WebCodecs guidance recommends moving per-frame processing off the main thread and supports transferring VideoFrame objects to workers; OffscreenCanvas can also move rendering off the main thread.
- A persistent RGBA8 GPU texture ring at 1920x1080 would require approximately 8,294,400 bytes per frame. At 30 fps for 15 seconds (450 frames), this is approximately 3.73 GB per camera and 7.46 GB for two cameras, before alignment, allocation overhead, additional render targets or metadata. At 1280x720 it is approximately 3.69 MB/frame, 1.66 GB per camera and 3.32 GB for two cameras. These are arithmetic estimates for one 4-byte-per-pixel RGBA8 texture per frame, not measured browser allocations. Alternative planar formats or texture-array layouts may change the result, but must be validated rather than assumed.

### Consequences for JudoReplayKit

1. Separate the display path from the retention path. `importExternalTexture()` may be a fast way to display the currently selected VideoFrame, but retaining the source frame to preserve that external texture can pin decoder resources. It is not a free long-term replay cache.
2. Test a persistent GPUTexture ring as a distinct candidate: decode into VideoFrame, copy each selected output into a preallocated GPU texture slot using `copyExternalImageToTexture()`, then promptly close the original VideoFrame. This may release decoder surfaces while keeping the cached image on GPU for fast display. Measure copy throughput, GPU memory, render latency, texture allocation limits and behavior under memory pressure.
3. Do not assume the persistent GPU texture ring is memory-cheaper than a CPU pixel ring. A straightforward RGBA8 cache is larger than tightly packed 8-bit 4:2:0/NV12 estimates by about 2.67x. It may be useful for rendering speed but can be prohibitive for 15 seconds of two-camera full-resolution history.
4. Compare persistent GPU textures against `VideoFrame.copyTo()` into CPU buffers and a compressed H.264 ring. The CPU copy may free decoder resources at the cost of CPU/system memory and later upload; GPU copy may avoid CPU round-trip but consumes dedicated/shared GPU memory.
5. Because WebGPU APIs are not Baseline and require a secure context, test the actual application origin. `localhost` is generally treated as a secure context, but an HTTP LAN-IP or hostname deployment must not be presumed secure. If the application must be opened remotely over the LAN, plan HTTPS or a non-WebGPU fallback.
6. Keep exact frame stepping and timestamps independent of rendering API. WebGPU should only render the already selected frame; it must not become the source of frame order or time.

### Updated buffer/render PoC matrix

- A: retain VideoFrames and render selected frames via WebGPU `importExternalTexture()`; measure decoder-surface retention and stall thresholds.
- B: copy VideoFrame pixels via `VideoFrame.copyTo()` into bounded CPU buffers, close source VideoFrames, then render selected frames through the chosen browser path.
- C: copy VideoFrames into preallocated persistent GPUTexture slots via `copyExternalImageToTexture()`, close source VideoFrames, and render from those GPU textures.
- D: compressed H.264 ring plus short decoded hot window; decode older positions from preceding keyframe and measure cold seek latency.
- Run all candidates at target resolution/fps with two cameras, two concurrent replay views, 5/15/30-second windows, and strict memory budgets. Record GPU dedicated/shared memory, system RAM, decoder stalls, decode queue depth, copy throughput, render latency, first-display latency, exact step correctness, live latency and recording continuity.

### Assessment

WebGPU offers a potentially efficient display path and a persistent GPUTexture copy could decouple cached images from decoder-backed VideoFrames. However, it does not provide a guaranteed zero-copy long-term store; persistent textures still consume substantial GPU memory, and WebGPU availability/security-context requirements make it an optional acceleration path. The strongest design remains a measured comparison of CPU pixel cache, GPU texture cache, retained VideoFrames and compressed-history/hot-window hybrid. No architecture is selected. Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — WebGPU texture-array limits and implications for a 15-second GPU frame ring

**Scope:** Review of current WebGPU device limits and texture creation validation. Research only; no runtime PoC, local changes, or architecture decision.

### Verified findings

- The current WebGPU specification defines `maxTextureArrayLayers` with a default device limit of 256. A 2D texture's `depthOrArrayLayers` cannot exceed the device's requested `maxTextureArrayLayers` limit.
- The default `maxTextureDimension2D` is 8192. The texture width and height must each be within that limit. These are API resource-shape limits, not a guarantee that a device has enough physical memory for a large texture allocation.
- WebGPU adapters may support limits better than defaults, but applications must inspect `GPUAdapter.limits` and request higher limits when creating the `GPUDevice`. A device is governed by the exact limits selected at creation. An application must not assume 450 array layers are available simply because one GPU happens to support them.
- With the default 256-layer array limit, a 15-second 30-fps ring (450 frames per camera) cannot fit in one 2D texture array. It would require at least two arrays per camera (e.g. 256 + 194 layers), or individually managed textures/another layout. At 60 fps (900 frames), at least four default-sized arrays per camera are required.
- If an adapter exposes a larger `maxTextureArrayLayers`, the application may request it, but this is an optional capability and should not be a cross-device requirement. Multiple arrays remain the portable baseline for a GPU texture ring.
- The earlier RGBA8 memory estimate remains applicable to the total pixel payload regardless of whether frames are arranged in one or several arrays: approximately 3.73 GB per 1080p camera and 7.46 GB for two cameras at 30 fps/15 seconds, before overhead. Splitting into arrays solves a layer-count constraint, not the memory cost.

### Consequences for JudoReplayKit

1. Any GPU texture-ring PoC must log both `adapter.limits.maxTextureArrayLayers` and the actual `device.limits.maxTextureArrayLayers`, along with requested limits and texture creation failures.
2. The implementation must support a default-limit layout (at least two arrays per 15-second 30-fps camera) or reject the GPU-cache path and fall back cleanly. Do not require elevated adapter limits.
3. Texture arrays are not evidence that the full buffer fits in GPU memory. Measure actual allocation, device loss, out-of-memory errors, GPU dedicated/shared memory and performance under both camera streams.
4. Given the raw RGBA8 payload cost, a full-resolution 15-second two-camera GPU texture ring remains a high-memory candidate even if array-layer limits are solved. Keep it as an experiment, not a presumed preferred architecture.

## 2026-11-15 — Worker-owned replay ring, SharedArrayBuffer requirements and asynchronous VideoFrame copies

**Scope:** Review of current WebCodecs, Web Workers, transferable ArrayBuffer and cross-origin isolation documentation. Research only; no runtime PoC, local changes, or architecture decision.

### Verified findings

- `VideoDecoder` is exposed in Window and DedicatedWorker contexts in the current WebCodecs specification. This permits a replay decoder and its output handling to live in a dedicated worker rather than the UI/main thread.
- `OffscreenCanvas` is broadly available and can be transferred to a worker, allowing rendering work to be moved off the main thread. Chrome's WebCodecs guidance recommends worker-based processing because per-frame callbacks can otherwise make the main thread less responsive.
- `ArrayBuffer` is transferable between workers. Transfer moves ownership of the memory resource and detaches the source-side buffer; it is not a second full pixel copy. This is useful for handing completed buffers between worker-owned stages, but a single owner for a ring is simpler than transferring each slot repeatedly.
- The current WebCodecs IDL declares `VideoFrame.copyTo()` destination as `AllowSharedBufferSource`, so a SharedArrayBuffer-backed typed array is permitted by the specification. SharedArrayBuffer availability in web content is gated by cross-origin isolation.
- To enable SharedArrayBuffer in a document, MDN documents `Cross-Origin-Opener-Policy: same-origin` together with `Cross-Origin-Embedder-Policy: require-corp` or `credentialless`, unless blocked by Permissions Policy. COEP can block cross-origin no-CORS resources unless the response opts in with CORP; CORS-mode requests must still pass CORS checks. This could affect an app whose UI, media server, fonts, scripts or other resources use different origins/ports, so it must not be enabled without an origin/resource audit.
- The current WebCodecs specification says promises returned by multiple `VideoFrame.copyTo()` calls are not guaranteed to resolve in the order they were invoked. A replay ring must therefore associate each copy with an explicit frame sequence, timestamp and reserved slot, and publish the slot as valid only after its own copy promise resolves. Ring wrap, reconnect epochs and late completion must not allow an older copy to overwrite a newer slot.
- `VideoFrame.format` is nullable. The specification says it is null when the underlying format does not map to a recognized VideoPixelFormat. `allocationSize()` and `copyTo()` without an explicit output format then throw NotSupportedError. An explicit RGB output format (`RGBA`, `RGBX`, `BGRA`, `BGRX`) invokes the conversion-to-RGB path, but this conversion and allocation must be measured and tested with hardware decoder output.

### Candidate worker arrangement for the PoC

1. Keep the UI thread responsible only for controls, live/replay overlay composition and user interaction.
2. Place each replay receiver's encoded ring, VideoDecoder, decoded-frame ring and timeline metadata in a dedicated worker (or a carefully partitioned shared worker if measurement proves appropriate).
3. Prefer a worker-owned bounded ArrayBuffer/TypedArray ring first. Use `VideoFrame.copyTo()` into reserved slots, record frame metadata separately, and close the VideoFrame promptly after the copy completes. Publish each slot only when its copy is complete and its epoch/sequence still matches.
4. Transfer an OffscreenCanvas to the worker for replay rendering where supported. The UI sends commands such as selected frame index, play/pause and camera choice; the worker renders the chosen frame. This avoids requiring SharedArrayBuffer merely to keep pixel history accessible to both threads.
5. Treat SharedArrayBuffer as an optional optimization only if simultaneous access from UI and worker is actually needed. Before enabling it, audit COOP/COEP effects on all same-origin and cross-origin resources and verify `crossOriginIsolated` at runtime.
6. Test VideoFrame.copyTo() with the actual hardware decoder output. Log `frame.format`, `allocationSize()` for the selected native or RGB format, copy latency, failures, per-slot sequence/timestamp, and output-surface release behavior. Do not assume every hardware decoder output exposes a directly copyable native pixel format.

### Consequences for JudoReplayKit

- A worker-owned ring is a credible way to protect UI responsiveness without introducing SharedArrayBuffer deployment constraints. It does not reduce the total decoded pixel memory requirement and it does not, by itself, isolate replay CPU/GPU usage from the live path.
- SharedArrayBuffer could permit low-overhead shared ring access, but the required cross-origin isolation headers may be operationally intrusive, especially if MediaMTX and Caddy endpoints use distinct origins or if third-party resources are present. Avoid making it a mandatory prerequisite.
- Explicit copy-completion ordering is now a required correctness test. A fast copy can finish after a later frame copy; the ring must not equate invocation order with completion order.
- The nullable VideoFrame format is an important hardware/software compatibility test. If a hardware output is opaque, the implementation may need explicit RGB conversion or a different rendering/cache path. This can change both CPU/GPU load and memory cost.

### Required PoC additions

- Compare main-thread versus dedicated-worker decode/copy/render while measuring UI input responsiveness and dropped frames.
- Compare worker-owned ArrayBuffer ring versus SharedArrayBuffer ring only on a cross-origin-isolated test origin; verify COEP does not block required media/API/assets.
- Deliberately delay selected copy promises or use a test harness to complete frame copies out of order; verify frame sequence/timestamp correctness and ring overwrite protection.
- Test `VideoFrame.format === null` handling and explicit RGBA conversion using actual hardware decoder output on Windows and Linux.
- Test worker termination, device loss, camera reconnect, decoder reset and ring generation changes; stale asynchronous copy completions must not republish invalid slots.

### Assessment

A dedicated worker owning the replay decoder, bounded copy ring and OffscreenCanvas is a strong next PoC arrangement because it protects UI responsiveness and avoids making SharedArrayBuffer/COOP/COEP a core deployment requirement. SharedArrayBuffer remains optional. Copy ordering and nullable hardware VideoFrame formats add two new correctness gates. No architecture is selected. Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — Candidate direct path: WebRTC encoded receiver transform into a worker-owned WebCodecs replay decoder

**Scope:** Review of the current W3C WebRTC Encoded Transform and WebCodecs specifications and MDN API documentation. This identifies a new topology candidate only; no runtime PoC, local changes, or architecture decision.

### Verified standards behaviour

- A receiver-side `RTCRtpScriptTransform` runs in a dedicated worker between the WebRTC receiver's depacketizer and native decoder. The worker receives `RTCEncodedVideoFrame` objects. The transform can inspect/modify/drop encoded frames; only frames written to the transform's writable side are passed onward to the receiver's native decoder. The W3C processing algorithm permits frames to be delayed or dropped, and the transform output cannot reorder frames.
- WebRTC encoded-transform Streams backpressure is disabled because WebRTC prioritizes low latency over reliability. A slow worker transform cannot assume that backpressure will pause media production. It must bound its own work and recover from overload.
- `RTCEncodedVideoFrame.data` is an ArrayBuffer. The current WebCodecs `EncodedVideoChunkInit` includes a `transfer` sequence of ArrayBuffers. If the data ArrayBuffer is included in `transfer`, the user agent MAY create the EncodedVideoChunk's internal media resource by referencing that data rather than copying it; the source ArrayBuffer is detached. This is a possible low-copy bridge from a dedicated replay receiver transform into WebCodecs, but zero-copy is not guaranteed.
- `EncodedVideoChunk` is immutable and serializable. It can be retained in a worker-owned compressed-history ring while being submitted to a WebCodecs `VideoDecoder`. The actual memory sharing and re-use cost must be measured; the specification allows reference-counted implementations but does not guarantee a particular backend allocation strategy.
- `RTCEncodedVideoFrame.type` provides `key` or `delta` classification. A key chunk can be decoded without previous frames; delta chunks depend on prior reference frames. The compressed ring must retain complete decode dependencies from a valid keyframe and preserve decode order.
- The current WebRTC Encoded Transform Working Draft defines `RTCEncodedVideoFrameMetadata.timestamp` as the media presentation timestamp (PTS) in microseconds. The long-standing `RTCEncodedVideoFrame.timestamp` property is marked deprecated/non-standard by MDN; new code must not rely on it. The metadata PTS field's actual browser availability must be feature-tested. If unavailable, derive a source-local monotonic PTS from unwrapped 90 kHz RTP timestamps, while separately retaining receiveTime/captureTime metadata where available.
- The same WebRTC Encoded Transform specification describes H.264 packetizer expectations such as Annex B NAL units separated by start codes. Actual access-unit framing and parameter-set delivery must still be validated for the chosen MediaMTX/browser path.

### New PoC topology candidate

Use a dedicated, continuously connected MediaMTX WebRTC replay reader per camera, separate from the visible live-view PeerConnection. Attach a receiver-side `RTCRtpScriptTransform` to that replay-only receiver and run the transform in a dedicated worker. In the worker:

1. Read each complete depacketized H.264 encoded access unit and its key/delta type and metadata.
2. Construct an `EncodedVideoChunk` from the frame data, using the ArrayBuffer transfer list where supported to allow the user agent to avoid a second copy. Do not enqueue the original encoded frame back to the WebRTC receiver's native decoder if this replay-only connection does not need a MediaStream video output; this is a candidate way to avoid a redundant native decode, and must be proven with runtime telemetry.
3. Retain the immutable chunk and metadata in a bounded compressed ring, preserving the complete keyframe-to-current decode chain, SPS/PPS versions, decode order, PTS and connection epoch.
4. Feed the same chunk to a dedicated warm WebCodecs VideoDecoder in that worker. Keep a bounded decoded hot cache for instant display/frame-step, with explicit VideoFrame closure on eviction.
5. Render selected replay frames through a transferred OffscreenCanvas overlay above the separate live-view video element. UI commands and frame-index acknowledgements cross the worker boundary; no pixel data needs to pass through the UI thread.

### Critical qualifications and failure handling

- This is not yet proof that a replay-only RTCRtpReceiver can omit all output frames while remaining a healthy, stable receive path across Chrome, Edge and Firefox. Verify that the PeerConnection remains connected, RTP continues to arrive, transform callbacks continue, and no native decoder allocation is required or triggered.
- `EncodedVideoChunkInit.transfer` only permits the user agent to reference transferred bytes; the standard says it MAY do so. Measure memory/copy behavior; do not label it zero-copy before evidence.
- The receiver transform is on the replay connection only. Keep the normal live-view PeerConnection free of this application transform to preserve the live isolation boundary.
- Since transform backpressure is disabled, bound `VideoDecoder.decodeQueueSize` and all worker queues. If decode falls behind, do not drop arbitrary dependent delta frames and continue as if the stream were intact. Mark a discontinuity, stop feeding dependent frames, recover from the next valid keyframe with required SPS/PPS, and record the gap.
- Use `getMetadata().timestamp` only when actually present. Do not rely on deprecated `RTCEncodedVideoFrame.timestamp`. RTP timestamps are source-local 90 kHz values and require wrap handling before conversion to microseconds; they are not a common clock between cameras.
- Test actual Annex B access-unit compatibility, SPS/PPS/multiple PPS, B-frame restrictions in MediaMTX v1.21.3, keyframe recovery, decoder reset, camera reconnect, and MediaMTX restart.

### Required PoC comparisons

- Compare: (A) separate replay PeerConnection + transform + WebCodecs decoder with original frames dropped; (B) separate replay PeerConnection + transform + WebCodecs decoder while also passing originals to native decode; (C) separate replay PeerConnection without transform plus browser-native decode/track processing.
- For each, measure RTP receive continuity, transform callback cadence, CPU/GPU, native decoder instances if diagnosable, WebCodecs decoder backend, decodeQueueSize, first output time, compressed ring bytes, decoded cache memory, live-view latency and recording continuity.
- Test both cameras simultaneously and two replay sessions; verify the replay receiver can warm continuously without influencing the visible live PeerConnection or MediaMTX recording.

### Assessment

This is a promising refinement: a replay-only WebRTC connection could deliver encoded access units directly to a worker-owned WebCodecs decoder, potentially avoiding an unnecessary second browser-native decode and keeping all replay work off the UI thread. The possible ArrayBuffer transfer path may reduce extra encoded-data copies, but the standard does not guarantee zero-copy. Dropping frames before the receiver's native decoder is standards-compatible in principle, but actual browser/connection behaviour must be demonstrated. No architecture is selected. Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — H.264 Annex B requirements for direct WebRTC-to-WebCodecs replay

**Scope:** Review of the W3C AVC (H.264) WebCodecs registration and WebRTC Encoded Transform receiver semantics. The AVC registration is a Group Note Draft/non-normative document; findings are interoperability requirements to test, not a guarantee of implementation support. No runtime PoC or local changes.

### Verified registration details

- The W3C AVC WebCodecs registration expects each EncodedVideoChunk to contain one H.264 access unit (one primary coded picture). For `avc` format, the chunk data is length-prefixed/canonical and `VideoDecoderConfig.description` contains an AVCDecoderConfigurationRecord. For `annexb` format, chunk data is Annex B byte-stream data.
- If `VideoDecoderConfig.description` is absent, the registration says the H.264 bitstream is assumed to be Annex B. This matches the format expected in many live-streaming pipelines, but must be confirmed from the actual MediaMTX receiver transform bytes.
- For Annex B, a chunk marked `key` is expected to contain an IDR picture and all parameter sets needed to decode its video NAL units. Merely marking an arbitrary intra-coded or recovery-point frame as `key` is not sufficient unless it meets the registration's random-access expectations.
- For `avc` format, the parameter sets are supplied through the decoder configuration description instead of the key chunk. The two modes must not be mixed: do not pass length-prefixed AVCC chunks with no description, or Annex B chunks with an incompatible AVCDecoderConfigurationRecord.
- The W3C registration explicitly states that WebCodecs implementations are not required to support AVC/H.264. H.264 support must be checked with `VideoDecoder.isConfigSupported()` and verified by decoding the actual camera stream.
- The W3C WebRTC Encoded Transform specification places receiver transforms between depacketization and the native decoder. The receiver transform output must preserve decode order; it may drop frames but may not reorder them. H.264 packetizer examples and expectations use Annex B start-code separated NAL units, but exact access-unit framing must be inspected in the actual browser/MediaMTX path.

### Implications for the direct replay worker

1. Prefer testing Annex B first for the live WebRTC path, with no `VideoDecoderConfig.description`, provided the transform bytes are proven to be complete Annex B access units.
2. Parse the SPS to derive the actual H.264 profile/compatibility/level codec string; do not hardcode a codec string from a guessed camera profile. Run `VideoDecoder.isConfigSupported()` for the derived configuration and then decode a real IDR-to-delta sequence.
3. At each random-access key chunk, verify that it contains the actual SPS/PPS set(s) required by all slice NAL units in that access unit. MediaMTX v1.21.3's inspected remuxer prepends one stored SPS/PPS pair at random-access points; this may be insufficient for multiple-PPS streams and remains a compatibility gate.
4. Record whether `RTCEncodedVideoFrame.type === 'key'` actually coincides with an IDR access unit for the source. Parse NAL unit types and slice PPS references; do not trust only the metadata key flag.
5. If the source or MediaMTX output does not provide a valid Annex B key access unit with all required parameter sets, either correct the upstream stream configuration/format path or reject that path for instant replay. Do not silently fabricate a key chunk.
6. Repeat with camera reconnects, MediaMTX restart, SPS/PPS changes, multiple PPS, long GOP, and the first key chunk received after a new replay reader joins.

### Assessment

The direct WebRTC-to-WebCodecs path has a clear standards-compatible bitstream contract, but it is strict: Annex B key chunks must be true IDR access units carrying every parameter set required for their slices. This directly intersects MediaMTX v1.21.3's one-stored-SPS/one-stored-PPS behaviour and the unresolved multiple-PPS issue. The path remains promising only if the actual camera bitstream passes this gate. No architecture is selected. Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — WebCodecs decoder optimizeForLatency hint for rapid replay output

**Scope:** Review of current WebCodecs VideoDecoderConfig and MDN decoder configuration documentation. Research only; no runtime PoC, local changes, or architecture decision.

### Verified finding

- `VideoDecoderConfig.optimizeForLatency` is a decoder hint. When true, the selected decoder SHOULD be configured to minimize the number of `EncodedVideoChunk` objects that must be decoded before a `VideoFrame` is output.
- The specification explicitly notes that user-agent and hardware limitations still apply and some codec bitstreams inherently require a minimum number of input chunks before output is possible. The hint cannot bypass H.264 reference dependencies, IDR requirements, SPS/PPS availability, or MediaMTX's B-frame restrictions.
- This is a decoder configuration option, not the encoder `latencyMode` setting. Do not confuse `VideoDecoderConfig.optimizeForLatency` with `VideoEncoderConfig.latencyMode = 'realtime'`.
- The hint may change decoder strategy and throughput/resource trade-offs. Its actual effect must be measured with the same bitstream on each browser/OS/hardware combination.

### JudoReplayKit PoC requirements

1. Include `optimizeForLatency: false` and `true` as separate decoder configurations in the replay decoder benchmark.
2. Cross each setting with `hardwareAcceleration: 'prefer-hardware'`, `'prefer-software'` and `'no-preference'` where the browser accepts the configuration.
3. Measure time from first valid IDR input to first VideoFrame output, steady-state decode throughput, CPU/GPU usage, decodeQueueSize, dropped access units, frame output cadence and resource pressure.
4. Repeat with both cameras simultaneously and the actual camera H.264 profile/GOP. A lower first-output latency on a single synthetic stream is not sufficient if throughput or stability degrades under two-camera load.
5. Do not call `flush()` after every chunk to force output. Normal continuous replay must keep the decoder configured and feed ordered chunks; flush/reset changes decoder state and requires a new key chunk.

### Assessment

`optimizeForLatency: true` is a low-cost-to-test candidate for the replay decoder and aligns directly with the immediate-first-frame requirement. It is not a replacement for a warm decoder, valid keyframes, or a decoded-frame cache. No architecture is selected. Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.

## 2026-11-15 — Experimental alternative: re-encode decoded replay frames as independent key chunks

**Scope:** Standards-based feasibility review of WebCodecs VideoEncoder key-frame controls and AVC registration. This is an exploratory cache alternative only; no runtime PoC, no image-quality measurements, no local changes, and no architecture decision.

### Feasibility

- WebCodecs `VideoEncoderEncodeOptions.keyFrame = true` requires the given frame to be encoded as a key frame. The AVC WebCodecs registration says an AVC-format key chunk is expected to contain an IDR picture, with parameter sets supplied in `VideoDecoderConfig.description`; Annex B key chunks are expected to contain an IDR picture and all parameter sets required by their slices.
- Therefore, in principle, a dedicated replay worker could decode each incoming original H.264 access unit, pass each decoded VideoFrame to a separate VideoEncoder with `keyFrame: true`, and store the resulting independent encoded chunks. Any stored frame could then be decoded from a single chunk rather than replaying a long dependency chain from an earlier camera IDR.
- The encoder can request hardware acceleration, but it remains a hint and actual backend/throughput must be measured. WebCodecs does not require H.264 encoder support on every implementation.
- `VideoEncoderConfig.latencyMode = 'realtime'` may prioritize low latency but the specification permits frame drops to meet bitrate/framerate targets and may sacrifice quality. `quality` mode must not drop frames to meet bitrate/framerate targets but may increase latency. For a referee review cache, dropped frames are unacceptable; encoder output must be monitored and gaps explicitly recorded.

### Major disadvantages

- This is a second lossy encode after the original camera H.264 decode. The WebCodecs AVC registration does not promise a lossless path or a uniform quality/quantizer interpretation across browsers and hardware. Fine detail can be lost or altered, which is especially concerning for referee review.
- Making every frame an IDR/key chunk removes temporal prediction and can substantially increase bitrate and storage compared with the original inter-frame H.264 stream. The actual expansion depends heavily on scene motion, resolution, quality settings and encoder implementation; no generic compression ratio should be assumed for judo footage.
- The pipeline adds decode plus encode work for both cameras, competing for GPU/decoder/encoder resources. Hardware encoding can also share finite codec resources with hardware decoding and the live display path.
- A re-encoded cache is a derivative preview, not a replacement for the continuously recorded original camera stream. Original recordings and their timestamps must remain authoritative and untouched.

### PoC design if lower-memory caches are needed

1. Keep the original compressed H.264 ring and continuous archive as authoritative sources.
2. In a dedicated replay worker, test an optional all-intra derivative cache using `VideoEncoder` and `keyFrame: true` on every decoded output frame.
3. Test `quality` mode first to avoid intentional frame dropping; test `realtime` only as a separate comparison and count every dropped/missing frame.
4. Compare H.264 AVC and any other genuinely supported independent-frame codec only after `VideoEncoder.isConfigSupported()` and real encode/decode verification. Store the matching decoder description/configuration with each cache generation.
5. Measure output bytes/frame and sustained bitrate on actual judo footage, encode latency, encoder queue size, GPU/CPU, decoder/encoder resource contention, two-camera stability, and exact one-frame-per-input correspondence.
6. Perform objective and visual quality comparison against the original decoded frame, including fast hand/foot contact, grip changes, boundary positions, small score indicators and motion blur. Reject if any material detail is lost or frames are missing.
7. Confirm that each encoded chunk marked key really decodes independently with a fresh decoder and the stored config; do not infer independent decodability from the requested keyFrame flag alone.

### Assessment

An all-intra derivative cache is technically feasible and could make arbitrary frame access simpler while reducing storage compared with raw decoded frames. However, its likely bitrate expansion, second-generation quality loss and extra encode load make it a lower-priority experimental fallback. It must never replace the original archive or be accepted without image-fidelity evidence. The preferred near-term PoC remains direct encoded ring plus a bounded warm decoded cache; all-intra encoding is an optional branch if memory tests fail. No architecture is selected. Overall status remains **CONDITIONAL GO for isolated PoCs only; NO-GO for architecture lock/full implementation**.
